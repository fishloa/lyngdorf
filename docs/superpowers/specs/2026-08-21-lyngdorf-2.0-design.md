# lyngdorf 2.0 — Architecture Design

Status: **final design, maintainer-ratified; no code changed yet**. Written
against 1.10.0 (`main` @ `ae31374`), issues #49/#50/#51, and the generated
surface inventory (`surface-2.0.md`). The seven open questions in earlier
drafts have been ruled on by the maintainer; §11 records each decision and
its reasoning. This document is the project spec for the 2.0 work.

This is a deliberate breaking release. Nothing is retained *permanently* for
compatibility's sake; every name that survives past 2.x survives because it
earns its place. One argued exception exists, and it is time-boxed: 2.0
carries a deprecation shim layer for the 1.x names — renames and relocations
only, never the deliberately-removed members, and never the property setters
— which is deleted in 2.1 (D9, §11; the original "no compatibility" wording
was softened for this and only this). The three drivers are the three Home
Assistant platinum requirements:

| Driver | Requirement | What 2.0 does about it |
|---|---|---|
| #49 | `strict-typing` — ship `py.typed`, honestly | `mypy --strict` clean over the whole package, marker in the wheel, enforced in CI |
| #50 | `inject-websession` — accept a caller-supplied aiohttp/httpx session | `create_receiver(..., session=aiohttp.ClientSession \| None)`; owned internally when absent, never closed when injected; all HTTP on aiohttp with no `run_in_executor` on any HTTP path (one bounded, avoidable UDP hop remains in discovery — D8, with platinum-tier precedent) |
| #51 | `async-dependency` — the write surface must be async | **Every member that sends anything to the device is `async def`. No property setters. No sync write path.** |

---

## 1. Design principles

These five rules generate the whole surface. Where a 1.x member survives or
dies, it is because of one of these, not taste.

1. **The async rule (one sentence, no exceptions):** *anything that causes a
   command to leave the process is `async def`; anything that reads cached
   state or edits an in-process callback list is sync.* Property setters
   cannot be `async`, therefore no writable properties exist. See §3.

2. **Capability is structural, not interrogative.** A feature the model lacks
   is an attribute that is `None` (a missing component) or a key absent from a
   mapping — never a method that raises at call time on some models, never a
   `has_*()` you must remember to consult, never a `*_range` that is `None`
   as a secret capability flag. `if receiver.zone_b:` replaces
   `has_zone_b_feature()`; `Trim.CENTER in receiver.trims` replaces
   `trim_centre_range is None`. The dividing rule: **fixed-per-model
   capability is structural; runtime-varying capability is a predicate.**
   Stepping is fixed per model, so a steppable control is a *subtype*
   (`SteppableControl`, §2.3) rather than a `can_step` flag you must
   remember to consult; `player.can_pause` genuinely varies with the
   current source, so it stays a live predicate (§5). Read-only
   *informational* values that are absent simply read `None`/empty —
   gating matters for writes, where calling the wrong thing sends a
   command the model does not define; a read cannot do harm. See §5.

3. **One shape per concept.** Every settable numeric (volume, Zone B volume,
   six trims, lipsync) is the same `NumericControl` object — value, advisory
   range, `set` — with `up`/`down` on the `SteppableControl` subtype where
   the model can step (§2.3). Every enumerated selection (source, sound
   mode, RoomPerfect position, voicing) is the same `noun` / `nouns` /
   `set_noun()` triple. Every subscription is `on_*(cb) -> unsubscribe`.
   This is what kills the 24-member trim block and the `async_pause` /
   `set_volume` / `volume_up` / `press` naming zoo. One shape also means
   one *consumer* shape per concept: §6 offers exactly one pattern per
   platform kind, never a recommended form alongside a tolerated one.

4. **The wire layers are private.** `LyngdorfReceiver` and its components are
   the entire public API. `LyngdorfApi`, `Msg`, `lookup_command`, the
   per-model `*_MESSAGES`/`*_CONFIG`/`*_INPUTS` constants, the ten
   model-specific receiver subclasses — all internal. What a consumer needs
   from the model layer (`LyngdorfModel`, `NumericRange`) stays public.

5. **Measured behaviour is sacred.** The paced coalescing queue, advisory
   ranges, lenient-inbound/strict-outbound enums, per-model command tables and
   every measured-evidence comment survive verbatim. §9 lists them; the
   implementation must move that code, not rewrite it.

Naming: the `async_` prefix is dropped everywhere (`connect`, `pause`,
`set_source`) — ruled, see D2 in §11. In 1.x the prefix distinguished the 9
async methods from 34 sync ones; in 2.0 there is nothing to distinguish —
*every* verb is async, so the prefix is pure noise. This matches how current
HA-ecosystem libraries are written (aioshelly, aiostreammagic:
`client.connect()`, not `client.async_connect()`); the `async_` convention is
an HA-core-internal style, not a requirement on dependencies.

The single receiver class is named **`LyngdorfReceiver`** (ruled by the
maintainer): a bare `Receiver` reads poorly once imported into a consumer's
namespace — the Home Assistant integration being the case in point, where
`Receiver` says nothing among a dozen other integrations' types. The ten
per-model subclasses still die (§2.9); `LyngdorfReceiver` is only the name of
what replaces them. Component classes (`ZoneB`, `Player`, `Remote`,
`NumericControl`) keep short names — they are reached as attributes of a
`LyngdorfReceiver` and imported mainly as typing targets, where the context
is already established.

**The one exception to "no compatibility retention", stated as the argued
decision it is (D9, §11):** 2.0 ships a deprecation shim layer — the 1.x
names for everything *renamed or relocated*, each emitting
`DeprecationWarning` and delegating to the new surface. The decisive reason
is mechanical: Home Assistant's `dev` must never be broken between PRs, so
under a clean break the version bump and all ~250 call-site adaptations
would be forced into one commit; the shims make every intermediate state
functional, so the migration lands as several small, bisectable PRs
instead (review risk is the secondary argument — D9 records both). The shims live exactly one release
and are deleted in 2.1 (the deletion is a recorded work item, §12, not an
intention). Two things are *never* shimmed, for reasons given in full in D9:
the 18 property setters (their removal is self-enforcing — assigning to a
read-only property is a static error, so the type checker finds every
consumer site — and no compatible shim could be safe anyway, since it would
be the synchronous enqueue #51 exists to remove), and anything the new
surface deliberately dropped (a shim resurrecting `lookup_command` would not
be compatibility, it would be un-removing it). Principle 1–5 above describe
the 2.x steady state; the shim layer is scaffolding with a demolition date.

## 2. The proposed public API in full

Everything below is the complete `lyngdorf` public surface. If a name is not
here or in §2.8, it is not public — with one time-boxed exception: for the
2.0 release only, the D9 deprecation shims (§7's "shim" rows) also resolve,
each emitting `DeprecationWarning`, until their recorded deletion in 2.1.

**Collection types follow one rule: `list` where the device's order is
meaningful and user-facing; `frozenset` where the collection is a
capability.** The selection lists (`sources`, `sound_modes`,
`room_perfect_positions`, `voicings`) and the informational tables
(`audio_inputs`, `video_inputs`, `stream_types`) are `list[str]` because the
device enumerates them in a defined index order — the same order its own
front panel and app present, which a consumer's dropdown should reproduce.
Capability sets (`Player.play_modes`, `Player.repeat_modes`, `Remote.keys`)
are `frozenset` because membership is the only question ever asked of them
and order would be an invented fact. Every collection in this section is
checked against this rule; none deviates.

### 2.1 Module-level

```python
async def create_receiver(
    host: str,
    model: LyngdorfModel | None = None,
    *,
    session: aiohttp.ClientSession | None = None,
) -> LyngdorfReceiver:
    """Create (but do not connect) a LyngdorfReceiver.

    With model=None, probes the device over :84 to identify it.
    Raises UnsupportedModelError if the reply names no supported model,
    TimeoutError/OSError on connection failure (propagated, as today).

    `session` is used for all :8080 streaming-module HTTP and is never
    closed by the library. When None, the library creates its own on
    first use and closes it on disconnect().
    """

async def discover_model(host: str, timeout: float = 5.0) -> LyngdorfModel | None:
    """Was async_find_receiver_model. Same contract: None for an
    unsupported model, TimeoutError/OSError propagate.

    Deliberately takes NO session parameter — this probes over raw TCP
    :84, not HTTP, and a session here would misstate what it does.
    Do not "complete the set" by adding one later."""

async def discover_ssdp_location(host: str, timeout: float = 5.0) -> str | None:
    """Unicast SSDP M-SEARCH to a known host, returning its UPnP
    description URL (the LOCATION header), or None.

    UDP only — no HTTP, no session. This is the one place the library
    retains a bounded, discovery-time-only executor hop (D8, §8);
    callers that already know the location (e.g. Home Assistant's own
    SSDP cache, `ssdp_location`) skip this function entirely."""

async def fetch_device_serial(
    location: str,
    *,
    session: aiohttp.ClientSession | None = None,
    timeout: float = 5.0,
) -> str | None:
    """Fetch the UPnP description XML at `location` and extract the
    device serial. Pure HTTP via aiohttp — no UDP anywhere on this path."""
```

**1.x's `async_get_device_serial(host)` is split in two, per #50's revised
plan** ("split what is there rather than grow it"): the UDP M-SEARCH and the
HTTP description fetch were one call, so every caller had to take the UDP
hop to reach the HTTP part. Now Home Assistant's flow passes the
`ssdp_location` it already has from core's SSDP cache straight to
`fetch_device_serial` and never touches UDP; manual entry — the path that
exists precisely because discovery did not see the device, e.g. the
maintainer's receiver on a different subnet — composes the two:

```python
if (location := await discover_ssdp_location(host)) is not None:
    serial = await fetch_device_serial(location, session=session)
```

Two functions rather than one `fetch_device_serial(host, *, location=None)`
keyword form, deliberately weighed: the keyword form is one call at both
call sites, but it bundles two transports behind one signature and leaves
`host` a dead — and potentially *contradictory* — parameter whenever
`location` is supplied (the fetch goes to the location URL; a mismatched
host would be silently ignored, a footgun no docstring fully defuses). The
split gives each function one transport and one job, makes every parameter
load-bearing, quarantines the executor hop behind a name that says UDP
discovery, and leaves the HTTP half session-injected and testable with no
UDP stub. Cost: the manual path is two awaits instead of one, in a
config-flow one-shot where that is negligible.

**Exactly two entry points carry `session`** — `create_receiver` and
`fetch_device_serial` — matching issue #50's updated spec. The second is not
optional sugar: Home Assistant's config flow calls it directly, before any
receiver object exists. `discover_model` (TCP `:84`) and
`discover_ssdp_location` (UDP) stay session-free by design, stated in their
docstrings so the asymmetry reads as intent, not omission.

`aiohttp` is a required dependency (ruled, D1): HA already ships it,
standalone users get it from any `pip install`, and an optional extra would
make `player` and `fetch_device_serial` import-time-conditional — poisoning
strict typing and doubling the test matrix for the benefit of two
non-streaming model families. Declared as a **range, never a pin** —
`aiohttp>=3.0.0`, the `airgradient` precedent from #50 — because Home
Assistant core controls the installed version and a pin would fight it; the
integration's manifest lists only `lyngdorf`, and pip resolves the range
against core's pin.

`create_receiver` stays a create-then-connect two-phase factory (unchanged
philosophy): HA registers callbacks between creation and `connect()`. It
returns `LyngdorfReceiver`, never `LyngdorfReceiver | None`, and raises a
typed `UnsupportedModelError(LyngdorfError)` instead of 1.x's
`NotImplementedError` — a library should not raise a builtin that normally
means "abstract method".

### 2.2 `LyngdorfReceiver`

```python
class LyngdorfReceiver:
    # -- identity / lifecycle -------------------------------------------
    @property
    def host(self) -> str: ...            # was str | None; host is required, so typed honestly
    @property
    def model(self) -> LyngdorfModel: ...
    @property
    def name(self) -> str | None: ...     # device-reported name
    @property
    def connected(self) -> bool: ...

    async def connect(self) -> None: ...
    async def disconnect(self) -> None: ...

    def on_change(self, callback: Callable[[], None]) -> Callable[[], None]:
        """Was register_notification_callback. Fires on any state change.
        Returns an idempotent unsubscribe; duplicate registration
        collapses to one entry. (Unchanged semantics.)"""

    # -- power -----------------------------------------------------------
    @property
    def power_on(self) -> bool | None: ...
    async def set_power(self, on: bool) -> None: ...

    # -- volume & mute ----------------------------------------------------
    @property
    def volume(self) -> SteppableControl: ...  # .value / .range / .set() / .up() / .down()
        # SteppableControl statically: every supported model steps volume (§2.3)
    @property
    def max_volume(self) -> float | None: ... # live MAXVOL; None on TDAI (unchanged docs/semantics)
    @property
    def muted(self) -> bool | None: ...       # was mute_enabled
    async def set_muted(self, muted: bool) -> None: ...

    # -- selections (one shape each: current / available / set) ----------
    @property
    def source(self) -> str | None: ...
    @property
    def sources(self) -> list[str]: ...       # was available_sources
    async def set_source(self, name: str) -> None: ...
        # raises LyngdorfInvalidValueError for a name not in sources (unchanged)

    @property
    def sound_mode(self) -> str | None: ...
    @property
    def sound_modes(self) -> list[str]: ...
    async def set_sound_mode(self, name: str) -> None: ...

    @property
    def room_perfect_position(self) -> str | None: ...
    @property
    def room_perfect_positions(self) -> list[str]: ...
    async def set_room_perfect_position(self, name: str) -> None: ...

    @property
    def voicing(self) -> str | None: ...
    @property
    def voicings(self) -> list[str]: ...
    async def set_voicing(self, name: str) -> None: ...

    # -- informational reads (None/empty when the model has no such thing)
    @property
    def audio_input(self) -> str | None: ...
    @property
    def audio_inputs(self) -> list[str]: ...      # was available_audio_inputs
    @property
    def audio_information(self) -> str | None: ...
    @property
    def video_input(self) -> str | None: ...
    @property
    def video_inputs(self) -> list[str]: ...
    @property
    def video_information(self) -> str | None: ...
    @property
    def streaming_source(self) -> str | None: ...
    @property
    def stream_types(self) -> list[str]: ...      # was available_stream_types

    # -- numeric controls -------------------------------------------------
    @property
    def trims(self) -> Mapping[Trim, NumericControl]: ...
        # only the bands this model has appear as keys (see §5)
    @property
    def lipsync(self) -> NumericControl | None: ...
        # None on the whole TDAI family. .range is the *live* LIPSYNCRANGE
        # value (seeded from the documented default), unchanged semantics.

    # -- components (None = model does not have the feature) --------------
    @property
    def zone_b(self) -> ZoneB | None: ...
    @property
    def player(self) -> Player | None: ...    # streaming module (:8080)
    @property
    def remote(self) -> Remote | None: ...    # remote-key surface
```

Documented write semantics, stated once on the class and inherited by every
setter's docstring by reference: **an `await` returns when the command has
been queued for paced delivery, not when the device has acted.** The
authoritative new state arrives through the device's own notification and is
observable via the properties / `on_change`. This is exactly 1.x's
enqueue-and-return behaviour with the loop requirement finally expressed in
the signature (#51); the `async def` is not a promise of confirmation, and
the docs must say so.

### 2.3 `NumericControl` and `SteppableControl`

One small hierarchy serves volume, Zone B volume, all six trims and lipsync:
`NumericControl` (value, range, `set`) and its subtype `SteppableControl`
(adds `up`/`down`). This is the collapse of the 24-member trim block plus
the 10 volume members plus the 3 lipsync members into one shape. Main-zone volume being a control object
rather than a flat float property is ruled (D5): `r.volume.value` costs one
attribute over `r.volume`, and buys volume, Zone B volume, trims and lipsync
being one shape, one test suite, and one HA entity class — a flat exception
for volume would have made the most-used control the only irregular one.

```python
class NumericControl:
    @property
    def value(self) -> float | None:
        """Current device-reported value in the control's unit
        (dB for volume/trims, ms for lipsync). None until first report."""
    @property
    def range(self) -> NumericRange:
        """Advisory (min, max, step). Never None — a model without the
        control has no NumericControl at all. For lipsync this is live
        (LIPSYNCRANGE overwrites the documented default). ADVISORY ONLY:
        set() sends the value unchanged, unchecked (issues #41-#43) —
        the device is the enforcement point. Do not reintroduce a bounds
        check."""

    async def set(self, value: float) -> None: ...


class SteppableControl(NumericControl):
    """A NumericControl whose model also has a step command. Stepping is a
    fixed-per-model fact, so per §1.2 it is expressed as a subtype, not a
    can_step flag: a non-steppable control simply has no up() to call, and
    there is nothing left to raise or to forget to check."""

    async def up(self) -> None: ...
    async def down(self) -> None: ...
```

Which controls are which is fixed by the protocol tables, and the
annotations are as *narrow as the facts allow*:

- `receiver.volume: SteppableControl` and `zone_b.volume: SteppableControl`
  — statically, no narrowing needed. Every supported model steps volume
  (MP/P via `VOL+`/`VOL-`, the TDAI family via its literal `VOLUP`/`VOLDN`
  tokens; Zone B exists only on MP/P, which step `ZVOL` the same way), so
  the subtype is a per-library fact, not a per-model one. If a future model
  cannot step volume, that is a real capability change and *should* surface
  as a type change.
- `receiver.trims: Mapping[Trim, NumericControl]` — the base type, because
  the mapping is genuinely mixed: every MP trim steps, TDAI bass/treble do
  not (no step command exists in that protocol). Which model is connected
  is a runtime fact, so a consumer narrows with
  `isinstance(ctl, SteppableControl)` before stepping — worked example in
  §6.3, and the narrowing itself is pinned by the §6.5 typing test.
- `receiver.lipsync: NumericControl | None` — base type; no model steps
  lipsync.

What a caller writes:

```python
await receiver.volume.set(-25.0)
await receiver.volume.up()                                 # SteppableControl statically
print(receiver.volume.value, receiver.volume.range)       # -25.0 NumericRange(-99.9, 24.0, 0.1)

await receiver.trims[Trim.BASS].set(1.5)
if Trim.CENTER in receiver.trims:                          # False on any TDAI
    await receiver.trims[Trim.CENTER].set(0.0)

bass = receiver.trims[Trim.BASS]
if isinstance(bass, SteppableControl):                     # False on TDAI, True on MP
    await bass.up()

if receiver.lipsync:
    await receiver.lipsync.set(20)
```

And what the HA integration writes — the payoff — one `NumberEntity`
implementation over every numeric control on the device (worked through in
full in §6):

```python
controls: dict[str, NumericControl] = {"volume": receiver.volume}
controls |= {f"trim_{band}": ctl for band, ctl in receiver.trims.items()}
if receiver.lipsync:
    controls["lipsync"] = receiver.lipsync
if receiver.zone_b:
    controls["zone_b_volume"] = receiver.zone_b.volume
# one entity class: min/max/step from ctl.range, value from ctl.value,
# async_set_native_value = ctl.set — no setattr strings, no typo risk (#49's motivating bug)
```

```python
class Trim(StrEnum):
    BASS = "bass"
    TREBLE = "treble"
    CENTER = "center"
    HEIGHT = "height"
    LFE = "lfe"
    SURROUND = "surround"
```

Spelling is American — `CENTER`/`"center"` — ruled by the maintainer. Enum
values are permanent public API strings, and American matches both Home
Assistant core's conventions and the device itself: the wire command is
`TRIMCENTER` (`models/mp_series.py`). **Scope of the rename, so the
implementer is not left guessing:** only surfaces a consumer sees change —
the `Trim.CENTER` member and its `"center"` value (and any entity keys the
HA side derives from it). Internal identifiers that never surface keep
their existing spelling untouched: `Msg.TRIM_CENTRE`,
`_trim_centre_callback`, `ModelConfig.trim_centre_range`,
`change_trim_centre` and kin are private, and respelling them is churn with
no consumer payoff.

Per-control wire encoding (the `trim_bass_treble_scale` 10-vs-1 split, #41)
is constructor-injected into each `NumericControl` from `ModelConfig` — the
control knows its scale, callers never see it. Unchanged behaviour.

`receiver.zone_b is None` on the whole TDAI family. Ten `zone_b_*` members

raise "unsupported".

### 2.5 `Player` (streaming module, `:8080`)

`receiver.player is None` on the TDAI-2170 and the whole P series — this
replaces `has_position` and `model.has_streaming_feature()` checks.

```python
class Player:
    # -- now playing -------------------------------------------------------
    @property
    def now_playing(self) -> NowPlaying | None: ...   # unchanged dataclass

    # -- position (contract unchanged, including the deliberate
    #    raw-vs-jump callback split and its docstrings) --------------------
    @property
    def position_ms(self) -> int | None: ...
    @property
    def position_updated_at(self) -> datetime | None: ...
    @property
    def position_percent(self) -> float | None: ...
    def on_position(self, cb: Callable[[int | None], None]) -> Callable[[], None]: ...
    def on_position_jump(self, cb: Callable[[int | None], None]) -> Callable[[], None]: ...

    # -- per-source, runtime-varying transport capability (unchanged) ------
    @property
    def can_pause(self) -> bool: ...
    @property
    def can_next(self) -> bool: ...
    @property
    def can_previous(self) -> bool: ...
    @property
    def can_seek(self) -> bool: ...
    @property
    def can_shuffle(self) -> bool: ...

    # -- transport ---------------------------------------------------------
    async def pause(self) -> bool: ...           # was async_pause; keeps the
                                                 # AirPlay-session-teardown warning verbatim
    async def next_track(self) -> bool: ...      # was async_next
    async def previous_track(self) -> bool: ...  # was async_previous
    async def seek(self, position_ms: int) -> bool: ...

    # -- play mode (unchanged union-of-two-lists semantics) ----------------
    @property
    def play_mode(self) -> PlayMode | None: ...
    @property
    def play_modes(self) -> frozenset[PlayMode]: ...     # was available_play_modes
    @property
    def shuffle(self) -> bool | None: ...
    @property
    def repeat(self) -> Repeat | None: ...
    @property
    def repeat_modes(self) -> frozenset[Repeat]: ...     # was available_repeat_modes
    async def set_play_mode(self, mode: PlayMode) -> bool: ...
    async def set_shuffle(self, shuffle: bool) -> bool: ...
    async def set_repeat(self, repeat: Repeat) -> bool: ...
```

The transport methods keep their 1.x `bool` return (ruled, D7): it encodes
"HTTP accepted vs network failure", which is real signal even though the
device lies about honouring (it answers HTTP 200 to anything). They also keep
raising `LyngdorfUnsupportedError` when the current source does not offer the
control — unchanged, for the unchanged reason: a return value alone can never
mean "honoured". The `can_*` properties remain per-source and runtime-varying;
they are deliberately **not** folded into the structural capability model of
§5, because they are not model capabilities — they change with every source
switch. `player is not None` is the model capability; `player.can_seek` is
the moment-to-moment one.

### 2.6 `Remote`

`receiver.remote is None` on the whole TDAI family (replaces
`has_remote_keys`).

```python
class Remote:
    @property
    def keys(self) -> frozenset[RemoteKey]: ...   # was available_remote_keys
    async def press(self, key: RemoteKey) -> None: ...
    async def send(
        self, commands: Iterable[str | RemoteKey], num_repeats: int = 1
    ) -> None: ...
```

`send` keeps `send_remote_commands`'s entire contract verbatim:
resolve-whole-batch-before-sending, case-insensitive strings, block repeats
(`123123` not `112233`), no `delay_secs` (the write queue owns pacing),
`LyngdorfUnsupportedError` naming the bad value and the supported set.
`press` still delegates to `send` so the two can never diverge. `RemoteKey`
string values are untouched — they are in consumers' YAML.

The HA remote entity becomes:

```python
async def async_send_command(self, command, **kwargs):
    await self._remote.send(command, num_repeats=kwargs.get(ATTR_NUM_REPEATS, 1))
```

### 2.7 Value types and enums (unchanged except as noted)

Public, importable from `lyngdorf`:

- `NowPlaying` — unchanged frozen dataclass.
- `NumericRange` — unchanged frozen dataclass; still advisory.
- `PlayMode`, `Repeat` — unchanged (2×3 grid model, wire strings stable).
- `Control`, `PlaybackState` — unchanged, **lenient `_missing_` preserved**.
- `RemoteKey` — unchanged, **strict, values stable** (consumer YAML).
- `Trim` — new (§2.3).
- `LyngdorfModel` — kept public (consumers branch on model identity and HA
  stores it in config entries), but slimmed: the ~50 command-table delegate
  methods (`volume_up_command`, `trim_lfe_down_command`, `has_*_feature`,
  `capabilities`, `supports_message`, …) move to the internal config object.
  Public remainder: the members, `.model_name`, `.manufacturer`. Everything a
  consumer used `has_*_feature()` for is now answered structurally on
  `LyngdorfReceiver`.
- Exceptions: `LyngdorfError`, `LyngdorfInvalidValueError`,
  `LyngdorfUnsupportedError` unchanged; new `UnsupportedModelError`.

### 2.8 Diagnostics

`lyngdorf.diagnostics` stays public and essentially as-is (it is the
ground-truth capture tool for spec-correction issues):
`probe_capabilities()` (was `async_probe_device_capabilities` — prefix drop
only), `CapabilityProbeReport`, `ProbeResult`. It talks raw `:84` and needs
no session.

### 2.9 Explicitly dropped (and why)

This table describes the 2.x *steady-state* surface. Some of these names —
the renames and relocations, e.g. the `set_*` write methods and the stepper

2.1 (D9, §11); §7's third column says which, per member. The removals
proper (subclasses, `lookup_command`, `un_register_notification_callback`,

property setters — the one thing a shim cannot safely be (D9).

| `set_volume`, `set_zone_b_volume`, `set_lipsync`, `set_trim_*` ×6, `set_room_perfect_position`, `set_voicing` (the #43 method shims) | They existed only because lambdas can't contain assignments and `setattr` strings defeat mypy. | `volume_up/down`, `zone_b_volume_up/down`, `trim_*_up/down` ×12 | Folded into `NumericControl.up()/down()`. |
| `un_register_notification_callback` | Dead weight since registration returned an idempotent unsubscribe. One way to unsubscribe, not two. |
| `lookup_command` on the receiver | Wire-layer leakage; internal. |

| `ModelCapability` protocol | Unused by consumers; internal. |

## 3. Async policy

**The rule:** *`async def` if and only if the call causes bytes to leave the
process (RIO enqueue included); plain `def`/property otherwise.*

Applied without exception:

- **All writes are `async def`** — power, mute, source, sound mode,
  RoomPerfect, voicing, every `NumericControl.set/up/down`, remote keys,
  transport, play modes, plus `connect`/`disconnect`. 31 sync write members
  in 1.x → 0 in 2.0.
- **All reads are sync properties.** They touch only cached state; making
  them async would be theatre and would wreck HA entity property access.
- **Callback registration is sync.** `on_change`/`on_position`/
  `on_position_jump` are pure list operations (`register_in_list`) — no
  event-loop interaction, thread-safe enough in practice, and HA calls them
  from async context anyway. They keep returning the idempotent unsubscribe.

**Why property setters cannot survive at all.** A Python property setter is
syntactically synchronous; there is no `await receiver.volume = x`. Any kept
setter would keep the exact hazard #51 measured — `asyncio.Event.set()` from
an executor thread — while looking like an innocent attribute write. Keeping
even one ("mute is so convenient") re-opens the trap and forces the docs to
carry a "except these, which must be called on the loop" footnote. Zero is
the only defensible number.

**Why no sync method mirrors either.** #51's closing argument: a reviewer
reads `async-dependency` ("no exceptions") literally, and a library whose
write path is callable synchronously invites the question every review.
Internally nothing changes — the RIO setters still enqueue into the paced
queue and return without waiting; the coroutine wrapper costs one loop step
and buys a signature that makes off-loop misuse impossible rather than
undefined. The `async def` additionally means a genuinely threaded caller has
a *correct* option (`asyncio.run_coroutine_threadsafe`) where 1.x had none.

**Enqueue-and-return is kept, documented.** Awaiting device confirmation per
write was considered and rejected: the RIO protocol has no per-command ack
(state changes arrive as unsolicited notifications, sometimes not at all for
no-ops), the coalescing queue deliberately *discards* superseded absolute
setters so "my write's reply" is not even well-defined mid-drag, and HA's
model is optimistic-write-plus-push anyway. This is stated prominently in the
`LyngdorfReceiver` docstring so nobody mistakes `await` for a round trip.

  clients; they contain no protocol knowledge of their own.

Estimated result: no module over ~650 lines, versus 1953/1513 today.

## 5. Capability model

1.x expresses "does this model have X" four different ways: `has_*_feature()`
methods, `*_range` returning `None`, `available_remote_keys` being empty, and
setters raising `LyngdorfInvalidValueError` at call time. 2.0 unifies to two
tiers:

**Tier 1 — model capability (fixed for the connection's lifetime):
structural.**

| Feature | 1.x check | 2.0 check |
|---|---|---|
| Zone B | `model.has_zone_b_feature()` / `zone_b_volume_range is None` | `receiver.zone_b is not None` |
| Streaming module | `model.has_streaming_feature()` / `has_position` | `receiver.player is not None` |
| Remote keys | `has_remote_keys` / empty `available_remote_keys` | `receiver.remote is not None` |
| Lipsync | `lipsync_range is None` | `receiver.lipsync is not None` |
| A given trim band | `trim_*_range is None` | `band in receiver.trims` |
| Trim stepping | undocumented (warn-and-ignore) | `isinstance(ctl, SteppableControl)` — a subtype, per §1.2's fixed-vs-runtime rule |
| Video | `model.has_video_feature()` | `receiver.video_inputs` non-empty (read-only feed; see below) |

The type checker now enforces the capability check: `receiver.zone_b.volume`
is `ZoneB | None` attribute access, which `mypy --strict` flags unless
narrowed — the check a 1.x caller could silently skip becomes one the
toolchain demands. This is the capability model and #49 reinforcing each
other. (§6.3 addresses the one place this collides with consumer lambdas,
and states the contract that resolves it.)

Consequence: the "capability check" half of `_require_capability` disappears
— you cannot call `set` on a control that does not exist. The *numeric*
non-validation stays exactly as-is (§9).

**Tier 2 — runtime capability (varies with source/session): predicates.**
`player.can_pause/can_next/can_previous/can_seek/can_shuffle`,
`player.play_modes`, `player.repeat_modes`. These are not model facts and
must stay live reads; folding them into tier 1 would be wrong (a `Player`
that exists still legitimately offers nothing while stopped). Methods guarded
by them keep raising `LyngdorfUnsupportedError`, for the measured reason
(device accepts anything with HTTP 200).

**Read-only informational feeds** (`audio_input`, `video_input`,
`video_information`, `streaming_source` and their `*_inputs`/`stream_types`
lists) are *not* gated: on a model without the table they read `None`/empty,
exactly as today. Rationale: gating exists to stop invalid *writes*; a read
returning `None` is already honest, and wrapping three read-only strings in a
`Video` component would be structure for its own sake. The 1.x behaviour
where an unrecognised wire value deliberately escapes the table (current
value not guaranteed to appear in the `*_inputs` list) is preserved,
docstrings included.

`max_volume` stays a plain nullable read — it is a live user preference, not
a capability, and the 1.x docstring war stories (0.0 dB is a real value; the
manuals contradict each other; never narrow `volume_range` with it) move over
verbatim.

**Consumer guidance for `max_volume` — because refusing to blend it into
`volume.range` leaves the consumer holding the problem, and this spec is
where that decision now lives.** The concrete failure if ignored: a UI that
maps a 0..1 slider onto `volume.range` alone will, with MAXVOL set to
−20 dB, offer a top region whose values the device silently clamps — the
slider jumps back on release (a wrong-constants variant of exactly this was
fixed in this library). The guidance, to be carried in `max_volume`'s
docstring and the README:

- **Bound the *displayed* maximum at `max_volume` when it is not `None`** —
  e.g. `min(volume.range.max, max_volume)` as the slider's upper bound —
  so the UI cannot offer positions the device will refuse.
- **Still send values unclamped.** The device is the enforcement point
  (§9 item 2); the library does not clamp, and neither should the consumer's
  write path — only its presentation.
- **Re-read `max_volume` on every `on_change`, never cache it once.** It is
  user-settable at runtime from the front panel or the official app; a
  cached copy is stale the moment someone touches the device.

Why the library does not do this itself: folding a mutable user setting
into `volume.range` would make a *capability* — something a consumer may
legitimately read once and build slider bounds from — silently change
meaning mid-session, so a stored scene or automation built against the old
bound would start meaning something different with no code change on either
side (the unchanged 1.x rationale). The library's job is to expose both
facts honestly and separately; combining them is a presentation decision
only the consumer can own.

## 6. The consumer contract: entity-description lambdas

**Hard requirement (maintainer-ruled).** The Home Assistant integration is
built from frozen entity-description dataclasses carrying small callables
that read and write library state. This is also where issue #43's bug came
from — in 1.x the write side had to be
`set_value_fn=lambda r, v: setattr(r, "trim_bass", v)`, a string attribute
name invisible to mypy, and the typo `"trim_bas"` shipped. 2.0 must support
this pattern cleanly, with no `setattr`, no strings, and every lambda checked
by `mypy --strict`. This section is the contract; a competent integration
author should be able to write the entity layer from it without guessing.

### 6.1 The boundary, and the coroutine-returning lambda

**One pattern per platform kind, per §1.3 — no recommended-and-tolerated
pairs.** The boundary is:

- **Anything whose subject is a `NumericControl` carries the control
  object** — number entities and stepper buttons. No lambdas. §6.2.
- **Everything else uses entity-description lambdas** — selects, switches,
  media_player transport, remote, sensors — because those have no control
  object to carry; their state lives as flat members on `LyngdorfReceiver`
  or on a gated component. This section.

There is deliberately no `control_fn: Callable[[LyngdorfReceiver],
NumericControl]` escape hatch for numbers: no framework constraint requires
one — an HA entity is an ordinary object that can hold the control — and a
contract offering a recommended form and a tolerated form gets both in the
wild.

For the lambda-shaped platforms, reads are ordinary expressions over sync
properties:

```python
current_fn=lambda r: r.source
is_on_fn=lambda r: r.muted
```

Writes are the linchpin. A lambda cannot contain `await` — but it does not
need to. Calling an `async def` returns a coroutine object, and
`Coroutine[Any, Any, None]` **is** an `Awaitable[None]`, so a lambda that
*returns the un-awaited call* satisfies `Callable[..., Awaitable[None]]`
under `mypy --strict`, and the entity awaits what the lambda returns:

```python
from collections.abc import Awaitable, Callable
from dataclasses import dataclass

from lyngdorf import LyngdorfReceiver

@dataclass(frozen=True, kw_only=True)
class LyngdorfSelectDescription(SelectEntityDescription):
    options_fn: Callable[[LyngdorfReceiver], list[str]]
    current_fn: Callable[[LyngdorfReceiver], str | None]
    select_fn: Callable[[LyngdorfReceiver, str], Awaitable[None]]

SOURCE = LyngdorfSelectDescription(
    key="source",
    options_fn=lambda r: r.sources,
    current_fn=lambda r: r.source,
    select_fn=lambda r, opt: r.set_source(opt),   # returns the coroutine; caller awaits
)

class LyngdorfSelect(SelectEntity):
    entity_description: LyngdorfSelectDescription

    @property
    def current_option(self) -> str | None:
        return self.entity_description.current_fn(self._receiver)

    async def async_select_option(self, option: str) -> None:
        await self.entity_description.select_fn(self._receiver, option)
```

To state it explicitly, because the whole pattern rests on it: **mypy
`--strict` accepts a lambda returning an un-awaited async-method call —
`lambda r, opt: r.set_source(opt)` against
`Callable[[LyngdorfReceiver, str], Awaitable[None]]`** — because the
lambda's inferred return type is the method's coroutine type, a subtype of
`Awaitable[None]`. No cast, no wrapper, no `# type: ignore`. This is pinned
by a CI typing test (§6.5) so it can never silently regress.

**Verified empirically before this spec was accepted**, with the project's
pinned mypy 1.19.1 against stub definitions of the proposed 2.0 shapes — the
claim is measured, not asserted:

```
lambda r, v: r.volume.set(v)      ->  Success: no issues found in 1 source file
lambda r, v: r.volume.st(v)       ->  error: "NumericControl" has no attribute "st";
                                             maybe "set"?  [attr-defined]
lambda r: r.zone_b.volume.value   ->  error: Item "None" of "ZoneB | None" has no
                                             attribute "volume"  [union-attr]
```

The first line is the contract. The second is the exact defect class that
motivated #43 and #49 — a mistyped attribute in an entity-description lambda —
now a review-time type error rather than a runtime `AttributeError` on a
user's device. The third confirms §6.3's gating contract is enforced by the
type checker rather than left to consumer discipline. (The measured stubs
exercised `NumericControl.set` and predate the §6.2 ruling that number
entities carry the control rather than lambdas; the three mechanisms they
verify — coroutine-return compatibility with `Awaitable[None]`, attr-typo
detection, and the `union-attr` gate — are method-agnostic and carry to the
lambda-side writes below unchanged. The §6.5 CI test re-pins them against
the lambda-side methods.)

The same shape covers every lambda-side write:

```python
# booleans (switch platform)
is_on_fn=lambda r: r.muted
set_fn=lambda r, on: r.set_muted(on)

# the other selects — sound mode, RoomPerfect position, voicing — are the
# same triple as SOURCE above:
select_fn=lambda r, opt: r.set_sound_mode(opt)

# transport (media_player) — Awaitable[bool], same mechanism, typed over
# the gated Player component per §6.3:
pause_fn=lambda p: p.pause()                                # Callable[[Player], Awaitable[bool]]
```

And the misuse that motivated #43/#49 is now caught at review time:
`lambda r, on: r.set_mted(on)` is a mypy error, not a runtime
`AttributeError` in someone's living room.

**What the pattern buys under API change — measured, not asserted.** A
lambda that *returns* the call is insulated from the sync→async
transition: when the method it returns goes async, the lambda text does not
change at all — it simply starts returning a coroutine instead of `None`.
The entire migration cost is one annotation per description class and one
`await` per entity method:

```python
-    set_value_fn: Callable[[Receiver, float], None]
+    set_value_fn: Callable[[LyngdorfReceiver, float], Awaitable[None]]
-        self.entity_description.set_value_fn(self._receiver, value)
+        await self.entity_description.set_value_fn(self._receiver, value)
```

The HA integration measured this against its real code: **zero lambda-body
edits** across the whole 1.x→2.0 sync→async transition (§7's migration
guidance carries the full payload table). A consumer calling methods
directly at each call site pays per site instead. This is not HA-specific
trivia — it is the reason to route writes through description callables in
any consumer: the indirection point absorbs signature transitions.

### 6.2 Numbers and steppers carry the control — the only number pattern

Every numeric is one `NumericControl`, so a number entity holds the control
directly. **This is the single supported shape for numbers; there is no
lambda-pair alternative** (§6.1's boundary):

```python
class LyngdorfNumber(NumberEntity):
    def __init__(self, control: NumericControl, description: NumberEntityDescription) -> None:
        self._control = control
        self.entity_description = description

    # Range plumbing: properties, not cached values — lipsync's range is
    # LIVE (LIPSYNCRANGE overwrites the documented default after connect),
    # and max/min/step must follow it.
    @property
    def native_min_value(self) -> float:
        return self._control.range.min

    @property
    def native_max_value(self) -> float:
        return self._control.range.max

    @property
    def native_step(self) -> float:
        return self._control.range.step

    @property
    def native_value(self) -> float | None:
        return self._control.value

    async def async_set_native_value(self, value: float) -> None:
        await self._control.set(value)
```

One entity class serves volume, Zone B volume, all six trims and lipsync,
with the model's real bounds and step (MP 0.1 dB vs TDAI whole-dB) flowing
from `ctl.range` — nothing hardcoded, nothing per-control. (The main-zone
volume entity should additionally bound its *displayed* maximum at
`max_volume` per §5's consumer guidance — presentation only; writes stay
unclamped.)

Stepper buttons are the same idea, one type narrower — the entity holds a
`SteppableControl`:

```python
class LyngdorfStepButton(ButtonEntity):
    def __init__(
        self,
        control: SteppableControl,
        description: ButtonEntityDescription,
        direction: Literal["up", "down"],
    ) -> None:
        self._control = control
        self._direction = direction
        self.entity_description = description

    async def async_press(self) -> None:
        if self._direction == "up":
            await self._control.up()
        else:
            await self._control.down()
```

How a setup path obtains a `SteppableControl` from the base-typed `trims`
mapping — the isinstance narrowing — is worked in §6.3.

### 6.3 Where lambdas meet Optional capability — the gating contract

Two places the structural capability model (§5) collides with lambdas, both
by design:

- `lambda r: r.zone_b.volume.value` — **fails `mypy --strict`**
  (`union-attr`: `zone_b` is `ZoneB | None`, and mypy cannot narrow an
  Optional inside a lambda) and would raise `AttributeError` at runtime on a
  model without Zone B.
- `r.trims[Trim.CENTER]` — raises `KeyError` on a model without that band.

**The contract that resolves this — stated as the contract, not a
suggestion:**

1. **Gate once, at setup time.** Entity creation iterates what the receiver
   actually has — `receiver.trims`, `receiver.zone_b is not None`,
   `receiver.player is not None`, `receiver.remote is not None` — and builds
   entities only for capabilities that exist. Capabilities are fixed for the
   connection's lifetime (§5 tier 1), so one check at setup is sufficient
   and final.
2. **Type each lambda over the narrowest object that owns the state.**
   Main-zone flat members → `LyngdorfReceiver`. Zone B members → `ZoneB`.
   Player members → `Player`. Remote members → `Remote`. Numerics use no
   lambda at all — the entity holds the control (§6.2). The gate in step 1
   has already produced the non-None component; hand *that* to the entity,
   and the Optional never appears inside a lambda.
3. **Never dereference an Optional component or index `trims` inside a
   lambda.** If a lambda contains `r.zone_b.` or `r.trims[`, it is wrong —
   and mypy will say so for the Optional case, which is the point: the
   library made the unsafe spelling unwritable, not merely inadvisable.

Worked setup-time gating (the number platform, complete):

```python
async def async_setup_entry(hass, entry, async_add_entities) -> None:
    receiver: LyngdorfReceiver = entry.runtime_data

    entities: list[LyngdorfNumber] = [LyngdorfNumber(receiver.volume, VOLUME_DESC)]

    # trims: iterate the mapping — only bands this model has are keys,
    # so a TDAI contributes bass/treble and an MP all six, with no
    # per-model conditionals here at all
    entities.extend(
        LyngdorfNumber(control, TRIM_DESCRIPTIONS[band])
        for band, control in receiver.trims.items()
    )

    if receiver.lipsync is not None:
        entities.append(LyngdorfNumber(receiver.lipsync, LIPSYNC_DESC))

    if (zone_b := receiver.zone_b) is not None:
        entities.append(LyngdorfNumber(zone_b.volume, ZONE_B_VOLUME_DESC))

    async_add_entities(entities)
```

And the stepper-button platform, showing the `SteppableControl` narrowing
(§2.3): `receiver.volume` is `SteppableControl` statically, so it needs no
check; each trim narrows with `isinstance`, and a button entity is created
*only* for controls that narrow — a TDAI, whose bass/treble cannot step,
simply gets no step buttons:

```python
async def async_setup_entry(hass, entry, async_add_entities) -> None:
    receiver: LyngdorfReceiver = entry.runtime_data

    entities: list[LyngdorfStepButton] = [
        LyngdorfStepButton(receiver.volume, VOLUME_UP_DESC, "up"),
        LyngdorfStepButton(receiver.volume, VOLUME_DOWN_DESC, "down"),
    ]

    for band, control in receiver.trims.items():
        if isinstance(control, SteppableControl):      # mypy narrows control here
            entities.append(LyngdorfStepButton(control, TRIM_UP_DESCS[band], "up"))
            entities.append(LyngdorfStepButton(control, TRIM_DOWN_DESCS[band], "down"))

    async_add_entities(entities)
```

The `isinstance` narrowing is standard mypy behaviour (narrowing a variable
to a subclass inside the guarded branch) and we have high confidence in it —
but per §6.1's own standard, that is a claim worth measuring rather than
asserting, so the §6.5 typing test includes exactly this loop, and the claim
is confirmed empirically there before the contract ships.

A scope note, so this example is not mistaken for the common path: the
primary consumer does not step trims at all — HA's `NumberEntity` has no
stepper concept, so trims only ever need `.value` and `.set()`, and its
only steppers are main-zone `volume_up`/`volume_down`, which type clean
without any narrowing because `volume` is `SteppableControl` statically
(§2.3). The mixed-mapping narrowing above exists because it is the correct
model and the library serves more than one consumer, not because of present
demand — implement it, pin it in the typing test, and build nothing further
around it.

And a Zone B description typed over the component, per rule 2 — note the
lambdas take `ZoneB`, not `LyngdorfReceiver`, so there is no Optional in
sight and `mypy --strict` is clean:

```python
@dataclass(frozen=True, kw_only=True)
class ZoneBSwitchDescription(SwitchEntityDescription):
    is_on_fn: Callable[[ZoneB], bool | None]
    set_fn: Callable[[ZoneB, bool], Awaitable[None]]

ZONE_B_MUTE = ZoneBSwitchDescription(
    key="zone_b_mute",
    is_on_fn=lambda z: z.muted,
    set_fn=lambda z, on: z.set_muted(on),
)

# constructed only inside:  if (zone_b := receiver.zone_b) is not None: ...
# the entity holds the ZoneB and applies the lambdas to it
```

The same idiom serves `Player` (media_player entity holds the gated
`Player`) and `Remote` (remote entity holds the gated `Remote`, §2.6). The
net effect: every lambda in the integration is total over its argument type
— there is no code path in which one can raise a capability error, and mypy
proves it.

## 7. Migration table (1.x → 2.0, complete)

This is the document the HA integration updates from. `r` = the
`LyngdorfReceiver`. "await" markers are part of the migration: every
right-hand verb is async.

**How to read this section — examples describe shapes, not files.** The
consumer's codebase is moving independently of this migration (PRs in
flight, entity-description adoption deepening), so nothing here quotes or
cites a consumer source file, and no baseline snapshot version is assumed —
a pinned example reads as precision but rots the moment either side moves.
Every worked example is written against the *pattern* ("wherever your
entity holds a `set_value_fn`, the annotation becomes
`Callable[..., Awaitable[None]]` and the call site gains an `await`"), and
the reader maps it onto their own code. Future editors: do not "helpfully"
pin these examples to a snapshot of any consumer's files. Measured figures
(site counts) are point-in-time *evidence of cost*, not checklists.

**The standard this section is written to** — for every member that
changes, a migrator must be able to answer four questions without asking
the library's authors, and the section will be reviewed against them:

1. **Where is my equivalent?** Keyed on the *old* name (what you grep
   for), exhaustively: the tables below were audited row-by-row against
   the full 1.10.0 surface inventory (18 writable properties, 46 read-only
   properties, 34 sync methods, 9 async methods, all module-level
   functions and re-exports) — every member appears, none is represented
   only by a category. **Additionally audited against a real consumer's
   actual usage**, which is the stronger claim: the HA integration
   mechanically extracted all 99 library members its code touches and
   diffed them against these tables — every one has a row.
2. **Is it shimmed, and until when?** The third column answers per member,
   never per category; every shim dies in 2.1.
3. **What breaks silently?** Rows that compile-but-misbehave carry an
   explicit **SILENT** marker (the reused-name reads: `r.volume` still
   compiles and returns a `NumericControl` where a `float` was expected),
   dual-duty capability guards carry a **HAZARD** marker (a `*_range is
   None` check naively renamed to `.range` fails only on the model the
   guard exists for), and test fixtures are their own silent class —
   `spec=` mocks accept stale flat assignments and fail at runtime inside
   correct production code (behavioural change 8, third done-when).
4. **What is the done-when?** Runnable criteria at the end of this section
   (Migration guidance), not "migrated".

The third column answers "can I defer this to a later PR?" per member (D9):

- **kept** — unchanged; no action.
- **shim** — the 1.x name still works in 2.0 as a deprecated delegate
  (emits `DeprecationWarning`), deleted in 2.1. Migrate in any later PR.
- **shim (now async)** — as above, but the 2.0 form is async where the 1.x
  form was sync. The alias is deliberately **sync-bodied and returns the
  coroutine** (D9's measured shape): the `DeprecationWarning` fires even if
  a legacy caller forgets to `await` — an `async def` alias would be a
  silent, warning-less no-op there. No #51 hazard: returning a coroutine
  executes nothing. The call site keeps its name and adds `await` in the
  bump PR.
- **await** — the name survives on the real 2.0 surface but is now
  `async def`; add `await` in the bump PR. Not a shim; nothing deprecated.
  Measured cost under the §6 entity-description pattern: **zero lambda-body
  edits** — a lambda that returns the call simply starts returning a
  coroutine; only the description class's annotation
  (`Callable[..., None]` → `Callable[..., Awaitable[None]]`) and the one
  `await` in the entity method change (§6.1).
- **bump PR** — removed outright in 2.0 with no shim possible (the D9
  carve-outs: property setters, and reads whose name 2.0 reuses at a new
  type); must change in the version-bump PR itself.
- **removed** — deliberately dropped (§2.9); never shimmed. Shims cover
  renames and relocations only, not removals.

### Behavioural changes beyond renames

1. Every write is `async def` and must be awaited (§3). Awaiting means
   "queued", not "confirmed" — same as 1.x's return.
2. Stepping a non-steppable control is unrepresentable: `up()`/`down()`
   exist only on `SteppableControl`, and a non-stepping model's control is
   plain `NumericControl` with no such methods (1.x logged a warning and
   did nothing; an interim draft ruled raise — superseded, see D4).
   `Trim.CENTRE`-style British spelling is gone: the member is
   `Trim.CENTER`, value `"center"` (§2.3).
3. `create_receiver` raises `UnsupportedModelError` instead of
   `NotImplementedError`, and never returns `None`.
4. Capability misuse is now largely unrepresentable (attribute on `None`,
   missing mapping key) instead of `LyngdorfInvalidValueError` at call time.
5. `aiohttp` becomes a required dependency (D1); `attrs` is dropped (its one
   use, `CountingNumberDict`, becomes a plain class).
6. Entity-description lambdas migrate from `setattr` strings to real calls
   per §6 — reads unchanged in shape, writes become coroutine-returning
   lambdas, Zone B/Player/Remote lambdas retype over the component.
7. Every "shim" row above emits `DeprecationWarning` in 2.0 and is deleted
   in 2.1 (D9, §12). On a "shim (now async)" row an un-`await`ed legacy
   call still performs no action, but it is *loud* — the sync-bodied shim
   warns unconditionally (D9's measured shape). The genuinely quiet hazard
   is the "await" rows (`set_room_perfect_position`, `set_voicing`): those
   are the real `async def` surface, so calling without `await` does
   nothing and nothing warns at the call. Either way the toolchain
   catches it — run the test suite with warnings-as-errors so
   `RuntimeWarning: coroutine ... was never awaited` fails loudly, and let
   mypy's `unused-coroutine` flag the site.
8. **Test doubles are a migration surface of their own, and the tool gates
   are blind to it.** Fixtures built as `MagicMock(spec=Receiver)` that
   assign flat attributes over reused names (`receiver.volume = -40.0`,
   `receiver.trim_bass = 3.0`) must become nested objects under 2.0 —
   and `spec=` will not flag the stale lines. Measured rather than
   trusted: a fixture write to a 2.0 read-only property is ALLOWED, and so
   is a write to an attribute not on the spec at all — `spec=` constrains
   attribute *names on read*, not writability and not type. The failure
   therefore surfaces at runtime as `AttributeError: 'float' object has no
   attribute 'value'` **inside production code that is itself correct**,
   caught by neither `mypy --strict` (mock attribute writes are untyped)
   nor any coroutine warning. The non-deferrable core follows the
   reused-name rule (a name 2.0 reuses on `LyngdorfReceiver` at a new
   type): `volume` and `lipsync` — no shim can bridge a fixture float to
   an object read there, by construction rather than by policy. The other
   fixture-written numerics (`zone_b_volume`, the six trims) defer: their
   flat names are free in 2.0 and shim to floats. See the payload table
   and the third done-when below.

### Migration guidance — measured payload and done-when

The bump PR's payload, **measured against the real HA integration** rather
than estimated (point-in-time evidence of cost, not a checklist — the
consumer's file layout will have moved by the time anyone migrates):

| Category | Sites measured | Shape of the change |
|---|---|---|
| Property assignments → `await set_*()` | 11, across 2 platform modules | one-liners already inside `async` methods; every site located by mypy's read-only `[misc]` error |
| Reused-name reads (`float`/`int` → control object; the **SILENT** rows) | 12, across 3 modules | add `.value` (or rewrite the number platform onto §6.2, below); every site located by the type mismatch under `mypy --strict` |
| Description-class annotation + entity `await` | ~one pair per platform (~8) | `Callable[..., None]` → `Callable[..., Awaitable[None]]`, plus one `await` in the entity method |
| Lambda bodies | **0** | a lambda that returns the call is untouched by sync→async — it starts returning a coroutine; §6.1 |
| Test-double rebuild (fixtures) | fixtures write **52 distinct library names** against production's **7** (production reads 60); test surface exceeds production at 1,876 vs 1,519 LOC, 68 library references in `conftest.py` alone | flat attribute assignments become nested mocks — one per control/component (`volume`, `trims`, `zone_b`, `player`, `remote`), each `spec`'d to its control/component class. **Non-deferrable in the bump PR: the reused names** (`receiver.volume = -40.0`-style lines for `volume` and `lipsync` — the moment the manifest moves, production reads `r.volume.value`) **plus fixtures for whatever reads the bump PR itself migrates**; the rest of the rebuild (e.g. `receiver.trim_bass = 3.0` — a shimmed flat read) tracks each deferred PR |

A correction stated plainly rather than folded in quietly: this table as
first measured covered **production only**, and the consumer's baseline
inventory shows that omitted the *larger half* — the fixture write surface
(52 distinct names) is **seven times** the production write surface (7).
Treat the test-double rebuild as the migration's larger half, not an
appendix.

Which fixture names are non-deferrable is decided by a **rule, not a
count** (an earlier draft mis-counted nine by using the wrong test —
"becomes an object somewhere" — so the rule is stated here precisely so the
membership cannot rot again): *a name is non-deferrable if and only if 2.0
reuses that exact name on `LyngdorfReceiver` at a new type.* That is
`volume` (now `SteppableControl`) and `lipsync` (now
`NumericControl \| None`) — exactly §7's two **SILENT** rows, no shim
possible **by construction, not by policy**: one name cannot be a float in
a fixture and an object in production. Every other fixture-written numeric
name defers: `zone_b_volume` and the six `trim_*` flat names are *free* in
2.0 (the objects live at `r.zone_b.volume` and `r.trims[Trim.X]`), so their
read shims return floats and the old fixture lines keep working until each
deferred PR migrates the corresponding reads. The bump-PR fixture work is
therefore the `volume`/`lipsync` rebuild plus whatever reads the bump PR
itself migrates — not a nine-name rebuild.

Measured qualifications and hazards worth carrying:

- **The number platform's reused-name reads are not per-site edits.** Under
  §6.2 that platform collapses to a single entity class carrying
  `NumericControl`s — a rewrite that is a net simplification (the measured
  case: a ~180-line module shrinks), not a migration cost paid seven times.
- **Do not forget diagnostics-style modules.** Read-only reporting code
  that dumps many properties and is exercised by few tests is exactly where
  a reused-name read hides: it compiles, and the report silently starts
  printing `NumericControl` reprs instead of numbers. The measured instance
  was a diagnostics module with three such reads (`volume`, `lipsync`,
  Zone B volume); grep any module like it for the **SILENT** rows' names
  explicitly, because no test will catch it for you.
- **Keep fixtures exhaustive over everything your code reads — the shim
  layer is not a substitute for that.** With shims present, an unset mock
  attribute yields an auto-generated child `MagicMock` rather than the
  loud `AttributeError` you would get with no shim on the class, so the
  failure surfaces later and further away from the cause. The consumer has
  already been bitten: a diagnostics module read ~40 receiver properties,
  the fixture defined about half, and the unset ones returned `MagicMock`
  objects — not JSON-serialisable — so the diagnostics response died
  *mid-serialisation*, presenting as a 60–90 second hang and a
  `ServerDisconnectedError` with nothing pointing at the cause. The fix
  was completing the fixture (theirs now sets every property that module
  reads, with a comment saying why). This compounds with the previous
  bullet deliberately: a reporting module is simultaneously where a stale
  relocated name hides *and* where an unset mock does the most damage —
  read-heavy, thinly tested, and it serialises its output.
- **Any 1.x `*_range is None` check was a capability check in disguise,
  and it never translates to `.range`.** `lipsync_range`,
  `zone_b_volume_range` and the six `trim_*_range` members all did double
  duty (`None` meant "no such control" — the exact "secret capability
  flag" pattern §1.2 abolishes). The mechanical rename
  (`r.lipsync.range is not None`) compiles, reads correctly, and fails
  only on the model the guard exists for; the correct translations are the
  structural checks (`r.lipsync is not None`, `r.zone_b is not None`,
  `Trim.X in r.trims`) — see the **HAZARD** markers on those rows.

**Done-when — runnable, not aspirational:**

- *Bump PR done* when the integration type-checks `mypy --strict` against
  `lyngdorf==2.0.0` with **zero `# type: ignore` added**, and its test
  suite passes with unawaited-coroutine warnings escalated to errors.
- *Fixtures done* — a third gate, because the two others are blind here
  (`mypy --strict` does not type-check `MagicMock` attribute writes, and a
  stale fixture raises no coroutine warning): **the fixture module
  constructs no library attribute that 2.0 types as an object.** The
  criterion is the type, so it tracks the reused-name rule automatically:
  in the bump PR that means `volume` and `lipsync` (2.0 types them as
  controls) plus nested mocks for any component (`zone_b`, `player`,
  `remote`, `trims`) the bump PR's own code reads. A scalar
  `receiver.trim_bass = 3.0` is *legitimate while that read is deferred* —
  the shim types it as a float — and becomes a violation of this same
  criterion in whichever PR migrates that read. Part of the bump PR by
  necessity, not choice. **This gate
  is a static grep by necessity, not by preference — do not "improve" it
  into a runtime assertion:** `spec=` does not constrain writes at all
  (measured), so a mock will happily accept a stale flat assignment — or
  even a name typoed during the migration itself — and no runtime
  mechanism can ever observe that a fixture set the wrong thing. Static
  inspection of the fixture source is the only vantage point that sees it.
- *Migration done* (and 2.1 thereby unblocked, §12) when the test suite
  additionally passes with `DeprecationWarning` from the `lyngdorf` module
  escalated to error — i.e. zero shim usage remains anywhere, fixtures
  included.

## 8. Session & lifecycle

### Injection and ownership (#50)

- `create_receiver(..., session=...)` stores the session on the
  `LyngdorfReceiver`; `fetch_device_serial` takes its own optional session
  (the config flow calls it with no receiver in existence). These are the
  only two session-bearing entry points; `discover_model` (TCP `:84`) and
  `discover_ssdp_location` (UDP) are session-free by design (§2.1).
- **Ownership is decided at construction, exactly as #50 specifies:**
  `self._owns_session = session is None`. An **injected session** is used
  for every `:8080` request (and discovery's UPnP description fetch) and is
  **never closed** by the library, per the `inject-websession` contract —
  HA owns it and passes `async_get_clientsession(hass)`. Only a session the
  library created for itself is ever closed.
- **No session supplied:** the ownership flag is still set at construction,
  but the owned `ClientSession` object itself is created lazily inside
  `connect()` — one deliberate refinement over #50's
  `session or aiohttp.ClientSession()` in `__init__`: constructing a
  `ClientSession` requires a running event loop, and `create_receiver` is
  the only 2.0 constructor path, which is already async, but keeping
  creation out of `__init__` also means a non-streaming model never
  allocates a session at all. `disconnect()` closes it; reconnect recreates
  it lazily. Standalone scripts see no behaviour change. The injected case
  is unaffected — #50's constraint that `async_get_clientsession` must be
  called on the loop is the *caller's* obligation and is naturally met in
  `async_setup_entry`.
- **Non-streaming model (TDAI-2170, P series):** `player is None`, the poll
  loop never starts, no session is ever created when none was injected;
  `disconnect()` has nothing to close. An injected session on such a model
  is simply held unused — harmless, and it keeps the factory signature
  uniform so HA does not need per-model conditionals.

### What the 2.0 restructure deletes from #50's plan

Issue #50 describes its plumbing path as
`async_create_receiver → MP60Receiver(…, session=…) → Receiver.__init__ →
LyngdorfApi → StreamMagicSession`, and calls threading the keyword-only
argument through the eleven subclasses (`MP40Receiver`…`P300Receiver` plus
the three family bases) "most of the mechanical work in this issue". **Under
2.0 that work does not exist.** The subclasses are deleted (§2.9); the
session goes to exactly one constructor — `LyngdorfReceiver.__init__`, which
hands it to `StreamingClient` — and the eleven-hop relay evaporates. This is
a concrete argument for doing #50 *inside* 2.0 rather than first against the
1.x shape: implemented pre-2.0, most of its diff would be plumbing that WP4
then deletes. The issue's stated plumbing path is superseded by this design
and describes work that will never be done; §7's migration table reflects
only the surface that actually ships.

### Discovery: split the call, keep the (bounded) UDP hop — D8, revised

After the four HTTP sites move to aiohttp, exactly one `run_in_executor`
survives: the unicast SSDP M-SEARCH (`device.py:1883`), UDP, not HTTP. An
earlier draft of this design ported it to a native asyncio datagram
endpoint on the argument that `async-dependency` "admits no exceptions" and
a literal reviewer could object. **The Home Assistant side has since
answered that question with evidence (#50, maintainer comments), and the
evidence overturns the rewrite.** The ruling, and why:

- **SSDP stays, and stays in the library.** It serves only *manually
  entered* hosts — the discovered path takes serial, description URL, model
  and friendly name from HA's own `SsdpServiceInfo` and never calls the
  library. But manual entry is the path that exists *for when discovery did
  not work*: the maintainer's own receiver sat on a different subnet from
  Home Assistant and never appeared in its SSDP list. Dropping the search,
  or making it standalone-only, would delete the fallback that makes manual
  setup work.
- **`async-dependency` empirically tolerates a bounded executor hop.** Of
  the 86 libraries behind platinum integrations, 17 use `run_in_executor`,
  `to_thread` or a thread pool — about one in five — several for exactly
  this class of blocking socket/system call: `xknx/io/util.py:93` offloads
  `socket.gethostbyname` (the direct parallel — a platinum integration's
  library doing blocking socket work in a thread), `aioshelly` offloads
  address resolution, `brother` offloads SNMP engine setup,
  `androidtvremote2` a cert-chain load, `aiowebostv` a blocking client
  call. The practical bar is "nothing blocks the event loop", not "no
  thread ever". A short, discovery-time-only, unicast hop is consistent
  with what is already merged at that tier.
- **Do not grow the library's discovery either.** HA owns SSDP scanning: 46
  integrations declare `ssdp:` matchers and receive info from the central
  scanner; the only core code issuing an M-SEARCH is that scanner. A native
  asyncio SSDP implementation in this library would cut against that,
  gain nothing on the discovered path, and buy datagram-protocol
  subtlety for a code path HA mostly bypasses.

So 2.0 **retains the executor-based unicast M-SEARCH as a deliberate,
documented, evidence-backed decision** — recorded here and in the code
comment above the hop, citing the precedent table, precisely so nobody
"fixes" it later. Consequently the library does *not* claim zero
`run_in_executor`: the honest claim is **no executor hop on any HTTP path,
and one bounded, discovery-time-only UDP hop that a caller can avoid
entirely.**

Avoidability is the actual improvement, and it comes from the split (§2.1):
1.x's `async_get_device_serial` performed the UDP search *and* the HTTP
description fetch in one call, so reaching the HTTP part obligated the UDP
hop. 2.0's `discover_ssdp_location` (UDP, hop lives here and only here) and
`fetch_device_serial(location, *, session=…)` (pure aiohttp) separate them:
Home Assistant passes `ssdp_location` from its own discovery cache and
never touches UDP; the manual-entry path composes the two exactly as 1.x
behaved. The residual hop is thereby *avoidable rather than mandatory* —
a strictly better outcome than rewriting it.

### The streaming client on aiohttp

`StreamMagicSession`'s job — *hold one connection, reuse it, survive stale
keep-alive, follow a device that declines reuse* — maps onto aiohttp like so:

- **Connection reuse:** aiohttp's connector pools per host; the poll loop's
  requests are sequential (the existing `asyncio.Lock` serialisation is
  kept in `StreamingClient`), so one warm connection is reused exactly as
  the hand-rolled session did. The few-connection-slots constraint (#29,
  #31) is honoured by serialisation, not connector limits — connector
  limits would be global on an injected shared session and must not be
  touched.
- **Stale kept-alive socket:** aiohttp surfaces it as
  `ServerDisconnectedError`; `StreamingClient` keeps the one-clean-retry
  rule (retry once if the request went down a reused connection, else fail).
- **Device declining keep-alive:** aiohttp natively honours
  `Connection: close` per response — the manual `will_close` bookkeeping and
  the `MAX_REUSE_FAILURES` latch are no longer needed and are dropped. The
  field-verified TDAI-3400 keep-alive evidence (@svwhisper) moves into
  `streaming/client.py`'s docstring so the history is not lost.
- **Long-poll timeout:** per-request `aiohttp.ClientTimeout(total=poll+5)`,
  same margins as today. Note that is the *helper-level* figure; 1.x adds a
  further +1 at the transport, so the real total is poll+6. "Same margins as
  today" means keeping 1.x's arithmetic byte-for-byte, not adopting the
  number written here.
- **Transport writes must NOT queue behind the poll loop's lock.** The
  serialisation above is scoped to the poll loop's own requests, and that
  scoping is load-bearing rather than incidental. In 1.x, transport writes
  (`pause`, `next`, `seek`, play-mode changes) deliberately bypass the poll
  session and take a fresh connection per write with an explicit
  `Connection: close`. Routing `Player`'s writes through the shared
  `StreamingClient` lock instead would make a user's pause wait on the
  in-flight long poll — **up to a full ~25 s cycle before the command leaves
  the process.** Press pause, nothing happens for twenty-five seconds.

  So `Player`'s writes keep 1.x's connection-per-write semantics. The lock
  guards the poll loop; it is not a general mutex over the `:8080` surface.
  This was found while turning WP1 into executable steps — the original
  wording said only that the lock covers "the poll loop's requests", which
  is true but reads as incidental, and an implementer consolidating "all
  HTTP through one client" would introduce the stall without noticing. It is
  stated here as a requirement so WP3 and WP5 cannot get it wrong quietly.
- **Error contract preserved:** helpers keep returning `None`/`False` on
  network/parse failure rather than raising — this is a reverse-engineered
  API with no stability guarantee, and the poll loop's
  backoff-and-reinitialise behaviour depends on it.
- **Cancellability:** aiohttp requests are genuinely cancellable, which
  retires KNOWN_ISSUES.md's only entry (the non-cancellable
  `http.client`-in-executor problem) and the 2-minute test-hang caveat with
  it.

### Connect / disconnect / poll (mostly unchanged, relocated)

`connect()` keeps the 1.x sequence exactly: register dialect callbacks →
open `:84` transport → paced setup burst (`SETUP_COMMAND_DELAY`, then start
the drain task — the burst must not be double-paced, per the existing
comment) → start monitor → start the now-playing poll only if the model
streams. The keepalive monitor, single-reconnect-task guard, single-poll-task
guard, exponential backoffs, power-gated polling (`set_power_state`), the
clear-now-playing-on-power-off behaviour, and mute requery on power-on (#26)
all move verbatim into `rio/client.py` / `streaming/poll.py`.
`disconnect()` additionally closes the owned session (never the injected
one).

## 9. Hard-won behaviours — preserved verbatim, with their comments

Non-negotiable carry-overs. The implementation moves this code; it does not
reinterpret it. Each item keeps its measured-evidence comment block:

1. **Paced, coalescing write queue** (`COMMAND_PACING_MS` = 50ms,
   `_coalesce_key`, `_ABSOLUTE_SETTER_SHAPE`, `ABSOLUTE_SETTER_MESSAGES`,
   per-model token derivation). The MP-60 ~16-command queue-depth cliff
   (issue #35) is the reason this library exists in its current shape.
   Absolute setters coalesce to latest; steppers, digits, cursor/navigation
   and queries never coalesce; sleep after *every* write, not just when the
   queue is non-empty. Remote keys can never coalesce because their tokens
   are structurally outside `ABSOLUTE_SETTER_MESSAGES` — that invariant and
   its comment survive.
2. **Advisory ranges, no setter validation** (#37/#41/#42/#43 history).
   `NumericControl.set` sends the value unchanged. The `volume_range`
   docstring explaining *why* the bounds check was removed (device clamps
   240/250/300/400 → 240 predictably) moves onto `NumericControl.range` /
   the relevant config fields. `max_volume` is never folded into
   `volume.range`, with the existing rationale.
3. **Lenient inbound, strict outbound enums.** `Control`/`PlaybackState`
   `_missing_` unchanged; `PlayMode.from_wire` returns `None` for unknowns;
   `RemoteKey` strict with stable string values.
4. **Per-model command tables and manual-is-wrong evidence.**
   `models/*.py` untouched in substance: TRIMTREB/TRIMTREBLE
   query-vs-reply mismatch, `!BACK` accepted despite MP manuals omitting it,
   MULTIVIEW P200-only, TDAI `trim_bass_treble_scale` (#41), TDAI volume
   ceiling +12 vs MP/P +24, MAXVOL absent from TDAI manuals, TDAI-2170
   fixed-table bitmasks, keepalive via DEVICE.
5. **Play-mode union** of per-source and global lists (each is a partial
   view of the 2×3 grid; taking either alone made `normal` unreachable) —
   verified on a real MP-60; comment survives on `Player.play_modes`.
6. **Position machinery:** raw-vs-jump callback split, drift tolerance
   (`POSITION_DRIFT_TOLERANCE_MS`), the unknown-state-is-not-a-discontinuity
   rule, the one-report pause-detection deferral (and its named test), the
   timestamp-refresh-on-repeated-value rule, and the deliberate asymmetry
   that play-mode changes fan out to `on_change` while per-second position
   does not ("do not fix it by adding position here too").
7. **Parsing details:** `_find_closing_paren` quote-aware scan (TDAI
   comma-packed names), CR/CRLF framing tolerance, comma-packed
   `LIPSYNCRANGE(min,max)` handling, unrecognised input values escaping the
   name tables.
8. **Connection hygiene:** never overwrite a live protocol without closing
   it (TDAI connection-slot leak), single reconnect task, single poll task
   with its cancellation-vs-completion slot rules, drop (not flush) the
   write queue on disconnect — each with its existing comment.
9. **`pause()` source-dependence warning** (AirPlay session teardown) —
   docstring survives on `Player.pause`.
10. **Callback registration semantics:** dedupe on register, idempotent
    unsubscribe, exception isolation per callback.

## 10. What deliberately did NOT change

- **`states.py` and `remote.py` in their entirety.** Both are recent,
  well-designed, and consumers' YAML depends on `RemoteKey` values.
- **`models/` structure and content.** `ModelConfig` stays a frozen
  dataclass; the per-family tables stay where they are. Only the
  `LyngdorfModel` delegate methods (public-surface leakage) go internal.
- **`NowPlaying`, `NumericRange`, exception class names.** Stable, correct,
  in use.
- **Two-phase create/connect.** A factory that also connects was considered
  and rejected: HA registers callbacks before connecting, and reconnect
  semantics are cleaner when construction is side-effect free.
- **Selection values stay plain strings** (source/sound-mode/voicing/RP
  position names). They are device-enumerated, user-editable strings, not
  closed sets — inventing enums for them would fight the device.
- **No renames of concepts that were already right:** `source`,
  `sound_mode`, `voicing`, `room_perfect_position`, `now_playing`,
  `connected`, `muted`-style booleans keep familiar names; `available_*` →
  plural-noun is the only systematic read-side rename, applied uniformly.
- **No command-layer features added.** No balance control, no HDMI output
  selection (`change_hdmi_main_out` was never surfaced publicly and stays
  internal), no DTS-dialog/loudness surface, no websocket `:80` channel —
  2.0 changes shape, not scope. Anything new rides on the clean base later.
- **Diagnostics module** kept as-is bar the prefix rename — it exists to
  file spec-correction issues and already does that well.
- **Tests' measured fixtures** (fake device transcripts) remain the source
  of truth; the port to the new surface must not weaken them (§13).

## 11. Decisions taken, and why (maintainer-ratified)

All seven questions raised during design were ruled by the maintainer as
recommended. Recorded here so the reasoning is not lost; the body of this
document already reflects each.

- **D1 — aiohttp is a required dependency** (not an optional extra). HA
  already ships it; standalone users get it from any `pip install`. An
  extra (`lyngdorf[http]`) would make `player` and `fetch_device_serial`
  import-time-conditional, which poisons strict typing and doubles the test
  matrix for the benefit of two models' users saving one wheel download.
- **D2 — the `async_` prefix is dropped.** With the entire verb surface
  async there is nothing left for the prefix to distinguish; it is an
  HA-core-internal convention, not an expectation on libraries, and current
  HA-ecosystem libraries do not use it.
- **D3 — `py.typed` ships in 2.0, not as a 1.11 pre-release — and strict
  typing is enforced from WP0, not retrofitted at WP6.** Annotating 1.x's
  `device.py`/`api.py` would mean typing ~120 signatures the rewrite
  deletes weeks later, and HA cannot reach platinum on 1.11 anyway
  (#50/#51 still open), so an early marker buys the integration nothing it
  can enable. The conclusion is now stronger than "fold the annotation
  work in": there is no bulk annotation pass at all. `mypy --strict` is
  gated per-module from WP0 (`[[tool.mypy.overrides]]` covering each 2.0
  module as it appears), so every line of 2.0 code is born strict-clean —
  a deferred second pass over freshly written code is exactly how the 127
  errors accumulated the first time. WP6 is left with only the 1.x
  remnants, the marker, and the wheel verification. This revises #49's
  original "own release ahead" plan; #49 should be updated to say so when
  work starts.
- **D4 (retired, superseded) — non-steppable `up()`/`down()`.** First
  ruled to raise `LyngdorfUnsupportedError`, replacing 1.x's
  warn-and-ignore. Superseded by the `SteppableControl` ruling: stepping is
  fixed per model, so per §1.2's fixed-vs-runtime rule it belongs on the
  structural side — `up()`/`down()` live on `SteppableControl(NumericControl)`
  and a non-steppable control simply has no such methods, so there is
  nothing to raise and no `can_step` flag to forget (the flag was exactly
  the "`has_*()` you must remember to consult" that §1.2 forbids, and the
  one capability the type checker could not enforce was the one that
  threw). The ergonomic cost is owned honestly: mixed collections like
  `trims` are base-typed and consumers narrow with `isinstance` (§2.3,
  §6.3); `volume`/`zone_b.volume` are `SteppableControl` statically since
  every supported model steps volume.
- **D5 — main volume is a `NumericControl`.** Cost: `r.volume.value` is one
  attribute longer than `r.volume`. Benefit: volume, Zone B volume, trims
  and lipsync are one shape, one test suite, one HA entity class; a flat
  exception for volume would make the most-used control the only irregular
  one.
- **D6 — TDAI-2170 and P-series support is retained.** They cost little
  (one dialect, config tables), and a breaking release that also dropped
  models would conflate two migrations.
- **D7 — transport methods keep their `bool` return.** It encodes "HTTP
  accepted vs network failure", which is real signal even though the device
  answers HTTP 200 to anything; changing to `None`-plus-raise would alter
  the poll-adjacent error style for no consumer ask.
- **D8 (revised) — the SSDP executor hop is retained, deliberately, and
  the serial lookup is split so the hop becomes avoidable.** An earlier
  draft ruled the opposite — port the M-SEARCH to a native asyncio datagram
  endpoint — on the argument that `async-dependency` admits no exceptions.
  Evidence from the Home Assistant side (#50) overturned that: 17 of the 86
  libraries behind platinum integrations use `run_in_executor`/`to_thread`/
  a thread pool, several for exactly this class of blocking socket call
  (`xknx` offloading `socket.gethostbyname` is the direct parallel), so the
  practical bar is "nothing blocks the event loop", not "no thread ever".
  SSDP itself cannot be dropped or made standalone-only — it serves the
  manual-entry path, which exists precisely for when HA's discovery did not
  see the device (the maintainer's own cross-subnet case) — and it must not
  be *grown* either, since HA owns SSDP scanning centrally. The useful
  change is the split (§2.1): `discover_ssdp_location` (UDP, the one
  retained hop) + `fetch_device_serial(location, *, session=…)` (pure
  aiohttp), so HA's flow feeds `ssdp_location` from core's cache and never
  touches UDP, while manual entry composes the two. The retained hop is
  documented at the code site with this precedent so nobody "fixes" it
  later; the library's claim is "no executor on any HTTP path", never
  "zero executors". Full reasoning in §8.

- **D9 — a time-boxed deprecation shim layer ships in 2.0 and is deleted in
  2.1.** Ruled at the consumer's request, and it amends §1's "no
  compatibility" stance as a deliberate, argued exception.

  **The primary justification is mechanical, measured from Home
  Assistant's actual release process: without shims, `dev` breaks between
  PRs, so a staged migration is impossible.** HA ships whatever is on
  `dev` at freeze time — no per-integration gate, no staging area — so the
  hard constraint is that `dev` must never be broken between PRs. Under a
  clean break, the manifest bump to `lyngdorf==2.0.0` and every platform's
  adaptation would have to land as a single commit: any intermediate state
  has the manifest on 2.0.0 while some platform still calls 1.x names, and
  `dev` would not import. A clean break therefore does not merely make the
  migration risky to review — it *forces* the ~250-call-site single PR as
  a matter of mechanics. The shims remove the constraint entirely: every
  intermediate state is functional (manifest on 2.0.0, un-migrated
  platforms working through deprecated aliases), so each platform PR is
  independently mergeable. A corollary, stated because it sounds alarming
  until the reason it is fine is written down: **an intermediate state
  does ship to users** — a release will carry 2.0.0 with shims still in
  use. That is acceptable precisely because the shims are functional
  rather than deprecated-and-broken: users get working code and at most a
  deprecation warning in the log.

  The secondary justification is **review risk** — real, but a quality
  argument where the above is a mechanical one. HA pins dependencies
  exactly (hassfest rejects ranges; zero of core's 1,199 manifest
  requirements use one), so the forced single PR would be reviewed as one
  unit against a dependency the reviewer cannot run, and this project's
  own recent history shows what large diffs hide: review of the remote-key
  work caught `num_repeats` nesting backwards, `BACK` wrongly removed from
  the MP models, and `MULTIVIEW` over-claimed on the P100/P300 — none of
  which a green suite caught. The shim layer lets the migration land as
  several small, bisectable PRs instead.

  Mechanics: every shim emits `DeprecationWarning`, delegates to the new
  surface, is strict-typed like everything else, and carries its own test.
  **The boundary is renames and relocations, nothing else** — the ruling's
  enumerated list (read renames, `set_*` write aliases, stepper aliases) is
  extended here to *all* renames and relocations (component reads like
  `now_playing`/`can_*`/`zone_b_*`, the `async_*` transport and lifecycle
  aliases, the module-level factory/discovery names), because the stated
  payoff — a small bump PR — only holds if relocated reads keep working
  too; a shim set drawn by rule rather than by list is also the only one a
  future reader can reason about.

  **Shim shape for a member that was sync in 1.x and is async in 2.0**
  (the `set_*` methods and every stepper — `volume_up`, `trim_*_up/down`,
  `press`, `send_remote_commands`): the shim is **deliberately sync-bodied
  and returns the coroutine**, never `async def`. An `async def` shim's
  body never runs unless awaited, so a legacy call site that has not yet
  added `await` would be a *silent* no-op that cannot even warn. The
  sync-bodied shape warns unconditionally, then returns the un-awaited
  coroutine for the caller to await:

  ```python
  def set_lipsync(self, ms: int) -> Coroutine[Any, Any, None]:
      """Deprecated 1.x alias. Deliberately sync-bodied: the warning must
      fire even when the caller forgets to await."""
      warnings.warn("set_lipsync is deprecated; use lipsync.set",
                    DeprecationWarning, stacklevel=2)
      return self.lipsync.set(ms)
  ```

  Both shapes were measured rather than trusted: under the pinned mypy
  `--strict`, an unawaited legacy call is flagged `unused-coroutine` for
  either shape (parity); at runtime, the sync shim emits 1
  `DeprecationWarning` on an unawaited call where the `async def` shim
  emits 0. Equivalent for typed consumers, strictly better for everyone
  else. **This is not a reintroduction of the property-setter hazard,
  though the shapes look superficially similar:** calling an async function
  returns a coroutine without executing anything — nothing enqueues, no
  `asyncio.Event` is touched — until the caller awaits it on the loop. The
  call site keeps its 1.x name, adds `await` in the bump PR, and renames
  later.

  **Relocation read shims are read-only properties, and must stay that
  way — measured, because an implementer will otherwise be tempted to make
  them settable "for fixture compatibility".** The measurement, against
  `MagicMock(spec=...)` fixtures that *write* the old names: with a
  read-only shim present, a fixture write is ALLOWED and an unmigrated read
  returns the fixture value; without any shim, exactly the same — the mock
  replaces the descriptor wholesale, so the shim body never runs in tests
  and a read-only property cannot block a fixture assignment either way.
  Settability would therefore buy fixtures *nothing* — and it would cost
  everything, because a settable shim **is a property setter**, the precise
  thing D9 carves out and the async rule forbids. What the read shim
  genuinely buys, so its purpose is not misunderstood as fixture
  compatibility: (a) real-device code paths, where un-migrated production
  reads the flat 1.x name against the real class; and (b) fixture reads of
  names no fixture set — with the shim on the class, `spec=` accepts the
  read; without it, the read is a loud `AttributeError`. That second effect
  cuts both ways — see §7's fixture-exhaustiveness warning and §13: with
  shims present, an unset mock attribute yields an auto-generated
  `MagicMock` downstream instead of an error at the read site.

  **The relocation-vs-removal audit, so the rule stays derivable.**
  Relocations — same information, new home — are shimmed: every
  `available_*` read, `mute_enabled`/`zone_b_mute_enabled`, the `has_*`
  capability predicates (`has_position` → `player is not None`,
  `has_remote_keys` → `remote is not None`, and `LyngdorfModel`'s
  `has_*_feature()` family — ruled explicitly: these relocate a capability
  fact into the structural model, they do not remove it), the component
  reads, the transport/lifecycle aliases, and the factory/discovery names.
  Genuine removals stay dead — `un_register_notification_callback`,
  `lookup_command`, `supported_models`, the ten receiver subclasses, the
  `const.py` compat exports, `ModelCapability`, and the `LyngdorfModel`
  command-table delegates (`*_command()`, `*_range()`, `capabilities`,
  `supports_message`, `config`, …) — shimming a removal would be
  un-removing it.

  **Not shimmed — the 18 property setters, and this carve-out is
  load-bearing.** The primary reason: **removing them is self-enforcing.**
  Assigning to a read-only property is a *static* error —

  ```
  error: Property "power_on" defined in "LyngdorfReceiver" is read-only  [misc]
  ```

  — so the type checker finds every affected call site for the consumer;
  none can be missed, and none can limp along unmigrated. A shimmed setter
  would keep compiling, keep the hazard, and *hide* the migration. The
  carve-out is therefore not a concession the library extracts from
  consumers — it is the safer half of the design. The secondary reason
  explains why a safe shim is impossible even if one were wanted: a
  compatible shim for `receiver.volume = -30` must be a synchronous
  property setter that enqueues, which means `asyncio.Event.set()` on
  whatever thread the caller happens to be on — precisely the defect #51
  exists to remove ("Non-thread-safe operation invoked on an event loop
  other than the current one", measured in Home Assistant). The hazard *is*
  the synchronous signature; no formulation is both compatible and safe.
  (Contrast the sync-bodied write shims above, which are safe because
  returning a coroutine executes nothing.) A future reader seeing an
  "incomplete" shim layer must not complete it.

  The carve-out's measured cost, recorded as evidence it is cheap: the HA
  integration has exactly **11 direct-assignment sites across 2 files** —
  `media_player.py` 9 (`power_on` ×2, `zone_b_power_on` ×2, `mute_enabled`,
  `zone_b_mute_enabled`, `source`, `zone_b_source`, `sound_mode`) and
  `remote.py` 2 — all one-liners already inside `async` methods.

  A second, smaller carve-out falls out of D5: the two names 2.0 *reuses at
  a new type* — `volume` and `lipsync`, whose 1.x float/int reads are now
  the control objects — cannot carry a shim either, since one name cannot
  be two things.

  Consequence for the consumer (the payoff — measured against the real
  integration, not estimated; full table in §7's migration guidance): the
  bump PR carries the 11 direct property assignments above, 12 reused-name
  reads (the **SILENT** class — `volume`/`lipsync` reads returning control
  objects where numbers were expected, including 3 in a diagnostics-style
  reporting module and 7 that dissolve into the §6.2 number-platform
  rewrite rather than being edited per site), and roughly one
  annotation-plus-`await` pair per platform. **Lambda bodies: zero edits**
  — a description lambda that returns the call absorbs sync→async
  unchanged (§6.1), which is §6's contract paying off before 2.0 even
  ships. Every site is toolchain-located (`[misc]` read-only errors for
  assignments, type mismatches for reused names, `unused-coroutine` for
  missing `await`s). Small tens of lines, not ~250 call sites; every
  rename and relocation — including the mock-fixture reads that dominate
  the consumer's test suite (measured: ~100 references, mostly mock
  attributes keyed on read names) — defers to its own later PR against
  the shims. The shims are deleted
  in 2.1 as a work item recorded now (§12): if the migration is unfinished,
  2.1 slips — the date follows the work — but the shims do not become
  permanent.

Also ruled: the receiver class is named **`LyngdorfReceiver`** (§1); the
entity-description lambda pattern is a hard supported contract with its own
section (§6) and CI typing test (§6.5); and exactly two entry points carry
`session` (`create_receiver`, `fetch_device_serial`) while `discover_model`
and `discover_ssdp_location` deliberately do not (§2.1).

  nothing about: if shim completeness were only verified during the
  consumer's migration, a missing shim would surface at WP8 — after
  hardware verification, with a release pending, the most expensive
  possible moment. Instead, a parametrised test in *this* suite runs
  against a committed JSON fixture of the consumer's measured 1.x usage:

  ```python
  @pytest.mark.parametrize("name", LEGACY_READS)
  def test_legacy_name_still_resolves_and_warns(receiver, name):
      with pytest.warns(DeprecationWarning):
          getattr(receiver, name)
  ```

    recording its provenance and measurement date; it is replaced
    wholesale when the consumer sends an updated inventory. The consumer
    has already produced it: 82 measured names, 82 classified, no
    duplicates across categories, none unclassified (`press` is absent

    test, not this fixture, covers the full shim spec including unmeasured
    members; the two tests answer different questions and both gate WP4).
  - **Nine categories, because the assertions genuinely differ by kind** —
    the original five could not hold everything without mis-filing:
    1. `shimmed_reads` — resolve and emit `DeprecationWarning`.
    2. `shimmed_write_methods` — D9's sync-bodied shape: the warning
       fires even when the call is never awaited.
    3. `shimmed_steppers` — likewise.
    4. `shimmed_methods_already_async` (`async_connect`, `async_pause`

    5. `shimmed_callbacks` (`register_notification_callback`,
       `register_position_jump_callback`) — renames returning an
       unsubscribe; the position one additionally asserts the no-op
       unsubscribe when `player is None`, since that conditional is its
       own behaviour.
    6. `await_same_name` (`set_room_perfect_position`, `set_voicing`) —
       the name survives on the real surface, sync→async only. **Not
       shims**: assert they are coroutine functions and do *not* assert a

    7. `kept_unchanged` (13 names) — the control group: assert *no*

       `receiver.volume = -40.0` would silently start "working" again

## 13. Risks

- **HA release coordination (reduced by D9's shim layer).** The
  coordination mechanism is Home Assistant's own exact-pin regime: hassfest
  rejects version ranges outright ("Requirement {req} need to be pinned
  <pkg name>==<version>"; zero of the 1,199 manifest requirements use a
  range), so the integration's manifest is already pinned `lyngdorf==1.x`
  and stays there — untouched by the 2.0.0 publish — until its bump PR
  moves it to `lyngdorf==2.0.0`. Publishing 2.0 to PyPI therefore cannot
  break an installed HA. What D9 removes is first the *mechanical*
  constraint (HA's `dev` must never break between PRs, which under a clean
  break forces bump-plus-adaptation into one commit — D9) and second the
  *review* risk that forced PR would carry: instead, the bump PR is a
  measured payload — 11 property assignments, 12 reused-name reads, ~8
  annotation/`await` pairs, zero lambda-body edits (§7's migration
  guidance) — with every rename and relocation deferred to its own small,
  bisectable follow-up PR against the shims, every intermediate `dev`
  state functional. Two release-mechanics notes measured from HA's repo:
  an intermediate state *will* ship to users (a release carries 2.0.0 with
  shims still in use) and that is fine because shims are functional, not
  broken — users see at most a log deprecation warning; and the bump PR is
  a **`.0`-release candidate needing beta exposure, never a patch-release
  passenger** — in `2026.8.1`, 8 of 18 commits were dependency bumps and
  every one touched zero Python files, whereas this bump changes ~30 lines
  of production code. Do not plan it into a patch release.
- **Residual risk introduced by D9: a shim layer that outlives its
  release.** Deprecation layers rot into permanent API when their deletion
  is an intention rather than a work item. Mitigations, all already in the
  design: the 2.1 deletion is a recorded §12 task with an explicit
  no-permanence clause; every shim warns on every call, so drift is
  audible in consumer logs and test output; the WP4 completeness and
  consumer-contract tests pin the shim set to §7's rows and the measured
  usage fixture, so it cannot quietly grow; and the shims live in one
  module deleted wholesale, not spread through the codebase.
- **Stated cost of D9, so the record shows what the decision bought *and*
  what it cost: shims convert a loud test failure into a quiet one.**
  Without a shim on the class, `spec=` rejects an unset mock attribute
  with an immediate `AttributeError` at the read; with the shim present,
  the same unset attribute returns an auto-generated `MagicMock` that
  fails somewhere downstream — measured in the consumer's diagnostics
  module as a 60–90 s hang and `ServerDisconnectedError` mid-serialisation
  with nothing pointing at the cause (§7's fixture-exhaustiveness
  warning). This is not an argument against shimming — production
  correctness wins and the mechanical `dev`-must-not-break argument (D9)
  is unaffected — but it is a real cost, mitigated only by the consumer
  discipline §7 states: fixtures stay exhaustive over everything the code
  reads, and the shim layer is not a substitute for that.
- **Strategic consequence of D3 + #50/#51 landing only in 2.0 — stated so
  nobody plans around a shorter runway:** Home Assistant cannot reach
  platinum until the entire 2.0 rewrite ships *and* the integration's
  migration PR lands and is reviewed. **Gold is the near-term ceiling**,
  and the platinum PRs are months out rather than weeks. This is accepted
  as the right trade (a 1.11 `py.typed` could not unlock platinum anyway
  while #50/#51 remained open), but it is a consequence, not an accident.
- **aiohttp connection behaviour vs hardware slots.** The serialisation
  lock (§8) is the safeguard; the hardware verification gate specifically
  watches socket count on a real device before release.
- **Test-port fidelity.** `basic_wiring_test.py` (4843 lines / 198KB) is
  the behavioural spec. WP4's port must be rename-only; any test whose
  assertion changes meaning gets called out in review explicitly.
- **A quality-scale reviewer challenges the retained UDP executor hop.**
  Low likelihood, prepared answer: the hop is bounded, discovery-time-only,
  avoidable via the `discover_ssdp_location`/`fetch_device_serial` split
  (HA's flow passes `ssdp_location` and never reaches UDP), and consistent
  with 17 of 86 platinum-tier libraries — `xknx`'s `socket.gethostbyname`
  offload being the direct parallel (D8, §8). The precedent is cited in the
  code comment at the hop so the answer travels with the code.
