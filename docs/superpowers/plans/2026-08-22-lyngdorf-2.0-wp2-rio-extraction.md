# Lyngdorf 2.0 — WP2 (`rio/` Extraction) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Plan 2 of 5** for the lyngdorf 2.0.0 release. Source of truth:
`docs/superpowers/specs/2026-08-21-lyngdorf-2.0-design.md` at commit `b10576d`.
This plan implements **WP2 only** (spec §12). Plan 1 covers WP0/WP1; plans
3–5 cover WP3–WP8. This plan assumes Plan 1 has already landed on the `2.0`
branch: `aiohttp` is a dependency, `attrs` is gone, the per-module strict
mypy gate exists, and `lyngdorf/streaming/` is a package.

**Goal:** Split `lyngdorf/api.py` (1513 lines) into the `rio/` package —
`protocol.py`, `queue.py`, `client.py` — per spec §4, and move the
per-family callback-registration logic out of `device.py`'s ten receiver
subclasses into data-driven dialect tables in `rio/dialects.py`. Nothing
about observable behaviour changes: every existing test passes with **zero
test-file edits**.

**Architecture:** `LyngdorfApi` (`api.py`) becomes a thin subclass of a new
`RioClient` (`rio/client.py`), which owns everything about the :84 wire
protocol that has no dependency on streaming state: the paced write queue,
connection monitor, reconnect loop, callback dispatch, and every
`power_on`/`volume`/`change_*`/`trim_*_up`/`trim_*_down` writer method.
`LyngdorfApi` itself keeps only what genuinely needs to coordinate the
streaming poll loop with the wire connection — `async_connect`,
`_async_establish_connection`, `async_disconnect` — plus all the
now-playing/position/play-mode state and poll-loop code, which spec WP2
explicitly leaves in place (WP3's job). Separately, `device.py`'s ten
receiver subclasses stop overriding `_register_*_callbacks` methods and
instead read a `Dialect` (a small frozen dataclass of `(Msg, attribute
path)` tables) selected by a `_dialect` class attribute — collapsing the
`_VideoZoneBReceiverMixin`/`MPReceiver`/`PReceiver`/`TDAIReceiverBase`/
`TDAI2170Receiver` override tangle into data plus one generic dispatcher.

**Tech Stack:** Python 3.11 · Poetry · mypy 1.19.1 (pinned binary) · ruff ·
black · pytest + pytest-asyncio. No new dependencies.

### What did not survive contact with the actual code

Read this before starting; it changes what several tasks below actually do
relative to the spec's one-paragraph description of `rio/`.

1. **`api.py` cannot fully dissolve into `RioClient` — `LyngdorfApi` has to
   keep `async_connect`/`_async_establish_connection`/`async_disconnect`.**
   The spec's module table describes `rio/client.py` as owning
   "connect/reconnect/monitor/keepalive". In the actual code, establishing
   a connection and starting the now-playing poll are coupled in exactly
   two places (`_async_establish_connection` starts the poll after
   connecting; `async_disconnect` stops it before closing the socket), and
   WP2 is explicitly forbidden from moving the poll loop (that's WP3).
   Rather than inventing connect/disconnect hook methods on `RioClient`
   that only exist to be overridden by the one subclass that will ever
   exist, this plan keeps those three methods on `LyngdorfApi` in `api.py`
   and moves everything else (monitor, reconnect loop, the write queue, all
   writer commands, callback dispatch) into `RioClient`.

   There is a second, harder reason `_async_establish_connection` can't
   move: `tests/reconnect_leak_test.py` does
   `monkeypatch.setattr(lyngdorf_api, "DEFAULT_LYNGDORF_PORT", port)` where
   `lyngdorf_api` is the `lyngdorf.api` module object. Python resolves an
   unqualified global name against the module a function was *defined in*,
   not the module of the class calling it — so if the line
   `loop.create_connection(..., self.host, DEFAULT_LYNGDORF_PORT)` moved
   into `rio/client.py`, that patch would silently stop working (it would
   patch an attribute nothing reads) and the test would try to connect to
   the real default port instead of the fake server. `_async_establish_connection`
   must stay textually in `api.py`, full stop — see Task 3.

   `api.py` therefore lands around **~700 lines**, not the spec's implied
   fraction of 1513. This is expected and intentional: it is exactly the
   streaming state and poll loop the spec's WP2 entry says stays "in place"
   until WP3 moves it into `streaming/poll.py`. Don't try to shrink it
   further in this plan.

2. **The registration logic moves as data, not as callable dialect
   objects that own behaviour.** The spec's dialects.py bullet describes
   "SRCNAME/RPNAME/VOINAME comma-packed parsing" as living in `rio/`. In
   the actual code those parsers (`_source_name_callback`,
   `_room_perfect_position_name_callback`, `_voicing_name_callback`, the
   TDAI-2170 fixed-table callbacks) are receiver-state-mutating instance
   methods on `Receiver` in `device.py`, and — more decisively —
   `tests/basic_wiring_test.py:4150-4152` calls
   `receiver._register_video_callbacks()` /
   `_register_zone_b_callbacks()` / `_register_surround_trim_callbacks()`
   directly, and `:4433-4448` calls `Receiver._populate_fixed_list(...)`
   as a static method. Both must keep existing, by those exact names, on
   the classes tests already import. So the dialect tables in
   `rio/dialects.py` hold only *which wire message routes to which
   receiver-callback attribute name*, per family; the callback method
   bodies themselves stay exactly where they are in `device.py`, untouched.
   This is also the more principled split anyway — the spec elsewhere
   states `rio/` "knows how to talk, nothing about what is said" (§4); the
   comma-packed name parsing is *what is said*, so it belongs with the
   receiver, not the wire client.

3. **`const.py`'s bottom-of-file `models` re-export cycle is real, but out
   of scope for this plan.** `lyngdorf/const.py:222` has `from .models
   import (...)  # noqa: E402, F401` — a genuine circular-import
   workaround (`models/__init__.py` imports `Msg` from `const` at its top;
   `const.py` imports `LyngdorfModel`/the `*_CONFIG` objects from `models`
   at its bottom, after `Msg` already exists in its own namespace). This is
   exactly the workaround spec §4 says 2.0 kills — but the spec assigns
   deleting `const.py`'s compat re-exports to whichever later WP removes
   the 1.x remnants (§2.9 lists it under "explicitly dropped", not under
   WP2 in §12). Neither `const.py` nor `models/` is in this plan's file
   list, and this plan does not touch them. Task 5's cycle check below
   verifies the **new** code (`rio/*`) introduces no new cycle; it
   deliberately does not attempt to fix the pre-existing one.

"""Per-family RIO registration tables (spec §4's "dialects").

Each `Dialect` enumerates, per registration group, which wire `Msg` routes
to which receiver-instance callback attribute - mirroring `Receiver`'s
`_register_*_callbacks` hooks in device.py (mute, source,
room_perfect_position, voicing, video, zone_b, surround_trim). This module
holds pure data: no receiver import, no `_register_callback` call, no
cycle. `Receiver` resolves each attribute path on itself with
`resolve_attr` at registration time and hands the bound callable to its
own `_register_callback`.

Callback *bodies* (parsing SRCNAME's comma-packed name, TDAI-2170's
bitmask tables, ...) are not here - they are receiver state mutation, not
wire-protocol knowledge, and stay on `Receiver` in device.py. This module
only says which message means which callback, per family.
"""

from __future__ import annotations

import dataclasses
from collections.abc import Callable, Sequence
from typing import cast

from ..const import Msg


def resolve_attr(receiver: object, path: str) -> Callable[[str, str], None]:
    """Resolve a possibly dotted attribute path against `receiver`, e.g.
    "_sources.count_callback" -> receiver._sources.count_callback.

    The cast is safe by construction, not by inspection: every path in
    the dialect tables below names either a `Receiver` callback method or
    a `CountingNumberDict.count_callback` - both always shaped
    `(self, param1: str, param2: str) -> None`. `getattr` cannot itself
    be typed narrower than `object` here, since `path` is arbitrary from
    mypy's point of view even though it never actually is at runtime.
    """
    target: object = receiver
    for part in path.split("."):
        target = getattr(target, part)
    return cast(Callable[[str, str], None], target)


def populate_fixed_list(
    target: "CountingNumberDict", fixed_names: dict[int, str], bitmask: str
) -> None:
    """Populate a dict of fixed, hardware-defined names filtered by a
    bitmask reply (e.g. TDAI-2170's SRCENABLED/RPSTATUS/VOIENABLED).

    Bit 0 is the least-significant bit, i.e. the rightmost character
    of the bitmask string, per the vendor manual.
    """
    enabled_indices = [i for i, bit in enumerate(reversed(bitmask)) if bit == "1"]
    target.count_callback(str(len(enabled_indices)), "")
    for index in enabled_indices:
        if index in fixed_names:
            target.add(index, fixed_names[index])
